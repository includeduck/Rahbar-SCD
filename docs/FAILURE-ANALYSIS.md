# Failure Analysis

This document records deliberate failure injections conducted across the RAHBAR pipeline stages, documenting the observed symptoms, forensic diagnosis paths as if encountered in production, and their engineering remedies.

---

## 1. Stage A · Extraction without OCR (Scanned Document Ingestion)

- **What we broke:** In `indexer/pipeline/extract.py`, disabled the optical character recognition fallback by commenting out the `pdf2image` and `pytesseract` branches in `_extract_pdf_pages()`, returning empty text for pages where `pdfplumber` extracted fewer than 20 characters.
- **Symptom:**
  - `faculty-entrepreneurship-and-technical-start-ups-policy.pdf` produced 0 chunks (down from 6 chunks).
  - `undergraduate-academic-rules-aug-2023.pdf` produced only 2 chunks from 26 pages (down from 106 chunks), missing 24 of 26 pages.
  - Queries concerning startup policies or 2023 academic rules returned irrelevant passages or triggered low-confidence fallbacks.
- **Diagnosis, as if we had not caused it:**
  - Running `pdffonts` against the raw PDF documents revealed zero embedded fonts for `faculty-entrepreneurship-and-technical-start-ups-policy.pdf`, confirming it is a pure bitmap scan:
    ```bash
    pdffonts corpus/raw/faculty-entrepreneurship-and-technical-start-ups-policy.pdf
    # name                                 type              encoding         emb sub uni object ID
    # ------------------------------------ ----------------- ---------------- --- --- --- ---------
    # (empty table)
    ```
  - Indexer structured logs showed page-level extraction producing empty strings:
    `{"logger": "rahbar.indexer.extract", "source": "faculty-entrepreneurship...", "page": 1, "chars": 0}`
  - The total chunk count in ChromaDB dropped from 710 to 600 chunks.
- **Remedy:** Reinstate the dual-mode extractor in `indexer/pipeline/extract.py`: pages with `< 20` characters of extractable text are rendered to 200 DPI greyscale images using `pdf2image.convert_from_path` and parsed via `pytesseract.image_to_string`, setting `Page.ocr = True` to track provenance.

## 2. Stage B · Fixed 100-Word Chunks Without Overlap (Structure-Blind Chunking)

- **What we broke:** In `k8s/base/configmap.yaml` and `indexer/pipeline/chunk.py`, replaced structure-aware recursive splitting with a naive fixed-window tokenizer setting `CHUNK_SIZE=100` and `CHUNK_OVERLAP=0`, discarding section headings.
- **Symptom:**
  - Total chunks stored ballooned to 1,540 chunks.
  - `recall@5` on `eval/run_eval.py` collapsed from `0.625` to `0.4375` (a 30% relative regression).
  - Citations became invalid: clause headings were separated from their operative text, causing `_filter_citations` to discard citations that no longer matched the golden section labels (e.g. clause numbers severed from clause titles).
- **Diagnosis, as if we had not caused it:**
  - Inspecting retrieved passages in ChromaDB revealed clauses truncated mid-sentence:
    `"Passage: ...shall be placed on academic warning if their CGPA falls below... [END CHUNK]"` followed in the next chunk by `"...2.00 at the conclusion of any regular semester."`
  - Neither chunk contained the section heading `"5.4 Academic Warning"`. Consequently, embeddings for queries like `"What CGPA triggers academic warning?"` matched fragmented definitions with low cosine similarity (< 0.65).
  - `eval/results.json` showed recall dropping drastically across `ordinary` and `version` categories.
- **Remedy:** Reinstate the structure-aware recursive chunker (`indexer/pipeline/chunk.py`): detect section boundaries via clause regexes (`^\d+(\.\d+)*\s`) and markdown headings, subdivide oversized sections at paragraph (`\n\n`) and sentence boundaries with 50 words of overlap, and prepend the active section heading to every chunk so semantic context is preserved in vector space.

## 3. Stage C · Retrieval & Embedding Model Mismatch (The Pin Guardrail)

- **What we broke:** In the API Deployment configuration, altered `EMBED_MODEL` to `all-minilm` while the Chroma collection remained indexed with vectors generated by `nomic-embed-text` (768 dimensions).
- **Symptom:**
  - All API Deployment pods refused to enter the `Ready` state (`0/1 Running`).
  - Kubernetes endpoints remained empty (`kubectl get endpoints -n rahbar rahbar-api` reported `<none>`).
  - Ingress traffic was rejected with HTTP 503 Service Unavailable, preventing user queries from being served.
- **Diagnosis, as if we had not caused it:**
  - Running `kubectl describe pod -n rahbar rahbar-api-...` showed failing readiness probes:
    `Readiness probe failed: HTTP probe failed with statuscode: 503`
  - Querying the `/readyz` probe endpoint directly revealed the exact mismatch guardrail triggered in `api/app/services/readiness.py`:
    ```json
    {
      "status": "not ready",
      "failed": "embed_model",
      "checks": {
        "chroma": "ok",
        "collection": "ok (710 chunks)",
        "embed_model": "embedding model mismatch: the index was built with 'nomic-embed-text' (dimension 768), but this api has EMBED_MODEL='all-minilm'",
        "redis": "ok"
      }
    }
    ```
- **Remedy:** Keep `EMBED_MODEL` declared in a single shared ConfigMap (`k8s/base/configmap.yaml`) referenced uniformly by both the indexer Job and the API Deployment via `envFrom: configMapRef`. Do not allow individual component manifests to override embedding model parameters.

## 4. Stage D · Generation Without Relevance Floor (Honest Abstention Failure)

- **What we broke:** Set `RELEVANCE_FLOOR=0.0` in `k8s/base/configmap.yaml` and disabled the floor check in `api/app/services/answer.py`, forcing all queries to invoke the LLM regardless of retrieval similarity scores.
- **Symptom:**
  - For deliberately absent questions in the golden set (such as hostel accommodation, meal plans, and room allotments which FAST Islamabad does not offer), the system attempted to generate answers rather than honestly declining.
  - The model returned hallucinated answers citing unrelated fee clauses (`fee-structure-page.html / Admission Fee` or `Miscellaneous Fees`).
  - Abstention correctness metric plummeted from `1.00` to `0.00` in `eval/run_eval.py`, triggering the CI regression gate with exit code 1.
- **Diagnosis, as if we had not caused it:**
  - Structured logs in `api` showed low similarity scores being passed directly to generation:
    `{"msg": "answered", "scores": [0.612, 0.608, 0.594], "answered_from_context": true, "citations_kept": 0}`
  - `eval/run_eval.py` reported:
    `q14 [abstain]: answered_from_context is True (expected False) -> FAIL`
- **Remedy:** Enforce a strict relevance floor (`RELEVANCE_FLOOR=0.60` or `0.50`) in `api/app/services/answer.py`. When all retrieved chunks have cosine similarity below the floor, short-circuit immediately: set `answered_from_context: false`, `citations: []`, `confidence: "low"`, and abstain without invoking the LLM.

## 5. Stage E · Retrieval Without Superseded Document Filter

- **What we broke:** In `api/app/retrieval/chroma.py`, removed the metadata filter `where={"superseded": {"$eq": False}}`, returning all matched chunks regardless of version status.
- **Symptom:**
  - When asked current policy questions (e.g., "What is the probation rule for students?"), the retriever returned passages from the superseded August 2023 rules instead of the current June 2026 Academic Rules Handbook.
  - The model cited `undergraduate-academic-rules-aug-2023.pdf` as authoritative for current regulations, quoting outdated criteria (such as old CGPA probation thresholds and course repetition policies that changed between 2023 and 2026).
- **Diagnosis, as if we had not caused it:**
  - Checking `AskResponse.citations` for queries on current policies revealed citations to `undergraduate-academic-rules-aug-2023.pdf`.
  - Comparing Chroma chunk metadata in the top 5 retrieved candidates showed chunks where `superseded == True` ranked higher than `superseded == False` chunks simply due to closer lexical overlap with the query phrasing.
- **Remedy:** Apply `where={"superseded": {"$eq": False}}` by default on all retrieval queries in `ChromaRetriever.retrieve()`. Only relax this filter when `_VERSION_RE` detects explicit user intent to query historical or repealed regulations (e.g., matching `"older version"`, `"previous rules"`, or `"august 2023 rules"`).
